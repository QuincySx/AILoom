# 开发知识：吸收、消化、修订与评估

本规格定义 AILoom 开发知识的组织原则、默认提示词和验收方法。分阶段编纂、独立 AI 评估、退回修订与评估后保存已接入；这不等于人工批准、完整代码快照或自动过期阻断。已有能力与待实现的运行机制分开列在文末。术语见 [CONTEXT](../../CONTEXT.md)。

## 项目隔离与关联页面

用户可以选择多个项目共用一份知识库 Git 仓库，也可以分别选择不同的仓库或直接指定项目知识目录。共用时，每个代码仓库在其中各占一个可读名称的文件夹。同一代码仓库的 Worktree 与受管子目录共用该项目文件夹；项目的原文、Wiki、索引和恢复状态按文件夹隔离，不混合编纂或检索。project_id 标识项目，knowledge_id 标识项目知识集合，都不表示必须另建一个 Git 仓库。

```text
agent-knowledge/                 # 一份 Git 仓库
  README.md                     # 项目导航
  app-monorepo--<项目UUID>/
    README.md                   # App 知识首页
    sources/                    # App 原始资料与笔记
    wiki/                       # App 模块与主题
    .ailoom/                    # App 内部记录与恢复状态
  hardware-js-sdk--<项目UUID>/
    README.md
    sources/
    wiki/
    .ailoom/
```

添加项目时选择“知识库仓库”，自动在其中使用“仓库名--完整项目UUID”子目录，并沿用该仓库作为后续新项目的默认位置。CLI 用 `--repository <知识库仓库>`，需要指定自选目录时可再使用 `--path <仓库内项目目录>`；已有目录属于另一项目时拒绝复用。现有 `--path` 仍表示精确的项目知识目录。项目关联与恢复声明记录具体项目子目录，同一个知识库 Git 仓库只需统一提交和同步；AILoom 的显式远端同步按配置的项目子目录写入，保留其他项目内容。

自动目录名保留仓库名称和完整项目 UUID；同名仓库、fork 与未共享身份的 clone 各占不同目录。新项目保存时一次生成并持久化 UUID，查看设置不预分配身份。恢复时按 UUID 和知识集合 ID 寻找已有目录，代码路径或名称改变不另建知识。既有目录和显式 `--path` 保持兼容；迁移需走预览、核对及切换，不能直接改名后遗留旧绑定。

旧版本混放资料的知识库通过 `ailoom knowledge --action separate --root <仓库> --path <项目目录>` 预览，再携带返回的 expected 执行。只复制当前项目有明确归属的原文、修订历史、主题页和恢复资源，生成新的知识库 ID，保留 project_id，切换当前仓库绑定；原共享库完整保留为备份。无归属的旧文档不自动分派给多个仓库，列入 unassigned_sources 并留在备份供后续核对。新机器恢复旧共享库时先登记待拆分身份，不恢复共享配置；拆分后若 recovery_required 为 true，须对新目录执行 recover。未应用的恢复配置不会被标记为可覆盖基线。

当前项目整理和召回均受项目归属限制。Wiki 已生成时，常规检索读取当前模块/主题、建议和问题页，不把原始导入、完整来源台账或历史变更页混入结果；原始证据由主题链接和 source_index 找回。尚无 Wiki 时原文可作检索线索，不能当成已编纂结论。项目经验和显式共享文档继续可查。共享库中的无归属旧文档不自动归给所有项目，状态须列出未纳入项。单项目旧库保持兼容；原有原文和旧报告保留，不静默迁移归属。新保存的项目经验使用项目目录，允许不同项目各自保存同名记录。

按模块、子职责和独立问题拆分，稳定 topic ID 对应独立页面；一个主题仅在一处完整陈述，关联用跨页链接。主题数量、篇幅和拆分按知识语义及可读性由 AI 判断，不以固定的 32 KB / 24 KB / 256 篇门槛拒绝整稿。重复章节合并、章节大小写兼容、主题导读保留，缺少索引时自动从主题生成导航；缺少自检记录时明确说明尚未评估。上游 HTTP(S) 参考链接可保留，保存不触发联网。完整来源目录单独保存，不挤入索引和每个模块。人工与 AI 编辑同一份正文，新增或改名无需更新机器清单；CLI 自动发现页面。生成前校验原文和现有正文指纹，写入中断可恢复；中断后若发现人工修改则停止恢复并保留现场。人工补充或改过的页面被本轮 AI 遗漏时继续保留，并加入首页导航。旧生成版本不作为当前召回对象，也不作为原始证据。结构转换本身不构成内容评估。

`knowledge --action reset-wiki --root <仓库>` 先预览，携带 expected 执行后将旧格式迁入上述目录并清空旧生成 Wiki，保留原文、恢复资源、使用反馈和归档状态。旧库根 README 若是原始资料则移入 sources/notes。操作暂留旧目录供恢复，既有知识库身份及项目关联不变。用户可通过正常整理重新生成；人工新增知识使用普通 Markdown，无需填写内部 ID 或维护清单。

项目 UUID 和知识集合 UUID 是归属依据，代码仓库 Git 地址是查询键，目录名仅用于浏览。代码项目 `.ailoom/knowledge.json` 和项目知识目录 `.ailoom/project/project.json` 保存代码仓库的无凭据地址；后者随知识仓库迁移，并与 `.ailoom/library.json` 的两个身份核对。初始化或保存恢复配置时记住明确地址及历史别名；地址不是远端所有权验证。SSH 别名无法直接确认正式地址时，可用 `init` 或 `checkpoint --repository-url <代码仓库Git地址>` 明确补充，不改写 Git 的连接配置或知识库同步地址。不同 clone、fork 或同名项目不会仅因 Git 地址相同而合并。

需要其他仓库知识时，AI 先运行 `ailoom --json knowledge --action locate --query <项目UUID、知识集合UUID、Git地址、本地路径或大概名称>`，只获取身份、项目知识目录、索引可用状态和后续查询参数，不读取或合并正文。名称可忽略大小写、空格及连字符；Git 地址沿用本机已明确保存的 SSH 映射，不猜测主机别名。根 package.json 明确声明的 repository URL 可作辅助依据，结果用 declared_repository_url 标明；持久化地址匹配用 saved_repository_url 标明，均不等同于核实远端。多个候选返回 ambiguous，须进一步用 UUID、Git 地址或路径消歧，不能按目录顺序挑一个。查询范围为本机登记与已选择的知识仓库；可用 `--repository <知识仓库本地目录>` 将范围限定到这一知识仓库，不要求登记或克隆对应代码。最多检查 8 层、10000 个目录，跳过隐藏目录，并在识别到项目目录后停止向其原文和 Wiki 正文目录遍历；未找到不能解释为远端不存在知识，查询不联网。

之后使用返回的 recall_command 按问题读取 SDK 自己的知识。有代码副本时使用 `knowledge --action recall --root <repository_root>`；仅有知识仓库时使用 `knowledge --action recall --path <knowledge_path>`，仍核对项目身份、逐项目隔离，并标记 code_available 为 false，不能据此宣称已核对当前代码。普通整理和召回不自动附带其他仓库的目录、依赖知识或全局知识清单；查找是显式、按需的操作。

## 维护什么

知识应帮助后续开发者或 AI 回答：业务如何运转、改动会影响哪里、当时为什么这样选、现在能否照做、什么变化要求重审。开发阶段与维护阶段可以有不同的合理选择；一个模块的限制不能自动推广到全仓库。

| 知识类型 | 必须保留的有效信息（有资料时） |
| --- | --- |
| 业务概念、规则与流程 | 概念、参与者、触发条件、状态转换、正常及异常路径、不变式、规则理由与例外 |
| 开发及协作流程 | 开发、测试、交付、回滚的步骤、约束、原因、适用条件和例外 |
| 模块与契约 | 职责、接口、依赖、跨模块影响、约束及不能破坏的语义 |
| 决策、妥协及技术债 | 当时目标、内部/外部约束、所选及被放弃方案、收益与代价、遗留问题、重审条件 |
| 问题与经验 | 现象、触发条件、调查与失败尝试、根因证据、缓解或修复、验证与局限 |

不是每条知识都填全部字段。未记录的理由明确留空缺，不从当前代码倒推历史动机。重复资料、频繁出现的说法和知名项目的做法都不能充当正确性证明。

## 三种内容职责

1. **原始资料**：保留原文及来源背景，用于重新解释和纠错。整理不能改写原文。
2. **当前知识**：按业务问题和模块组织当前有依据的规则、实现与经验，每项写清适用条件。未知、实验和建议有显式标记。
3. **决策历史**：保留旧做法、当时理由、后来改变的条件及证据，链接后继结论。压缩过程，不抹去理解取舍所需的因果。

这些职责通过独立原文、索引与主题页及保留的历史版本表达。旧生成稿可辅助比较，不能充当原始证据。

## 吸收：先保存，再判断

各 Worktree、主目录和受管子目录的材料逐步汇入同一项目。保存原文、文档相对路径、来源目录、分支、提交及未提交状态；采集时间不等于知识生效时间。相同正文可复用快照，来源分别保留；文档修订保留原版本。

当前候选清单只列每个来源文档的最新快照；被替代版本的项目归属与出处仍通过 `historical_source_origins` 按需查询。整理稿可引用已登记的历史原文，用于演变、冲突及未采用说明；发布时核对文件存在和内容哈希，不因它不在最新清单中拒绝整稿。历史原文不自动提升为当前证据，也不恢复用户停用的资料。未知、缺失或被改动的引用显示具体路径及原因；历史原文或出处在整理期间变化同样阻止过期结果覆盖。

结构或引用无法确认时，程序将具体诊断与完整草稿作为本地任务文件交回同一工具，最多修订两次；启动请求仍不超过 64 KB，草稿正文不拼入请求。AI 自行阅读相关原文、历史出处及必要代码，不能把程序诊断当作内容错误的裁决，不能伪造来源或只为过关删除有效知识。每份诊断草稿保存在操作记录中。修订仍未解决或修订工具不可用时，显示“整理稿待修订”，保留草稿与原因，当前 Wiki 不替换；不把未保存标成已保存或评估通过。人工修改、位置/项目冲突、文件越界和存储失败不触发模型重写，取消仍停止本次任务。

用户只需开始整理。后台先保留本仓库工作目录内的原文与出处；AI 接收项目目录、知识目录和编纂规则，自主列目录、搜索本地 Markdown、按内容识别开发知识，并核对相关代码。程序不再要求 AI 先读完全部资料清单与出处表；索引只用于按需核对归属、分支和历史。不要求用户扫描、勾选、导入，也不以已有知识或采集数量为零禁止 AI 发现本地文档。页面可查看范围，已删除工作目录仍使用此前保存的原文。

候选资料不等于已经认定的开发知识。当前自动收集 Markdown、MDX、reStructuredText 和 AsciiDoc 文本，排除认证、依赖、构建目录、知识库自身及其副本、嵌套独立仓库。AI 按内容判断相关性和证据性质，综合有效知识，对模板、无关内容和缺少原始证据的生成稿注明未采用原因；示例、测试夹具和外部项目的做法不得误写成当前仓库事实。单文件 4 MB、每个工作目录 2000 篇 / 64 MB 的读取边界及无法读取项交给编纂者，在结果中披露；未读取诊断达到 100 项时停止该目录的后续读取并说明，知识库容量不足时跳过未能保存的候选资料，预留结果空间，继续整理已有证据。不能把有限的文档覆盖声称为整个代码仓库审计。图片、PDF、Office 文档的内容提取尚未接入。

CLI 启动请求不超过 64 KB，只包含编纂规则、当前项目的代码及知识目录、原文目录、Wiki 目录和按需查询入口。无论资料数量多少，都不在启动请求中拼接文档清单和逐条出处。完整资料资格、来源背景、固定工作目录范围、旧 Wiki 页面及未读取记录保存在临时任务文件中，通常按 48 KB 分段；超长单条记录完整保存在独立文件中，提示工具按范围读取。AI 先自行发现 Markdown，需要追溯或消歧时再查询具体记录；相同原文的多个来源分别保留，分段不截断资料范围。仓库中新发现但尚未归档的文档用仓库相对路径及行号引用并标记未归档，不能伪造库内原文链接。生成结果仍按实际阅读披露覆盖，不能把目录扫描、清单存在或自动采集算作全文审阅完成。任务结束、失败或取消后清理临时文件，不改原文和当前 Wiki。

整理按“规划 → 模块批次 → 汇总核对 → 必要修订”执行。先用少量代表资料判断规模，列出模块、阅读/代码核对入口、优先级与预计耗时，再按约 20 分钟可交付的批次编纂；应用在每次 CLI 返回时持久保存计划和阶段稿。规划目标约 5 分钟，其他阶段目标约 20 分钟；达到阶段目标先通过控制文件请求返回已有成果，不终止正在收尾的 CLI。本批还有未阅读范围时，由 AI 在答复末尾标记继续，应用保留此前部分成果并接着处理同一批次，不误跳到下一模块。规划格式有偏差时保留原答复并按该计划作为一批继续，不因格式差异丢掉内容。阶段稿只提供工作线索，汇总仍回到真实原文与代码，覆盖按实际阅读披露，未完成项不能写成已审阅。

每轮总预算为 120 分钟，从开始整理时计时，包含采集、规划、全部批次、汇总及修订，不为每个 CLI 调用重新计时。启动前告知模型剩余时间、绝对截止时刻、分批目标与收尾协议，并提供可读取的控制文件；模型在每组读取前核对控制状态。90 分钟进入收尾，不再启动新批次，运行中的模型应停止扩大范围并返回已有成果和未完成事项；已有全部批次可在预留窗口中汇总。收尾窗口结束仍不退出的进程才由应用停止，显示“待继续”，保留已返回内容，当前 Wiki 不替换。用户可从页面继续阶段稿，也可重新规划；继续时预算重新开始，但旧阶段稿仍须核对当前资料和代码变化，不能跨项目采用。

服务每 15 秒报告总耗时及距最近输出的时间；连续 15 分钟无输出提示关注工具状态，静默本身不触发终止，也不等于工具已卡死或连接错误。主动取消始终可用。日志管道持续排空，内存只保留 64 KB 诊断末尾，日志总量不触发杀进程；正文采用知识库已有的 128 MB 存储预算，在工具结束后检查，超过容量也不在生成中途终止工具。每 15 秒检查正文变化并在工具退出时保留可用草稿，取消、异常退出及后续保存冲突都保留已收到正文和先前阶段稿，明确标为未完成或未保存，不当作正式知识。工具尚未返回正文时，不宣称已恢复其分析过程。只在明确认证失败时提示检查登录，预算、输入超限与其他工具错误分别报告。

开始按钮会自动批准本轮明确列出的本仓库工作目录，后台逐一检查目录授权并固定本轮范围；排队后新出现的 Worktree 不自动加入这次任务。该批准不需要用户再次扫描或逐篇选择。

记录中“已经完成”“测试通过”是来源主张，不等于整理者本次验证。删除来源 Worktree 不删除已采集证据；原文快照和来源记录才是长期出处。不同分支资料不能合并成“主分支已经如此”。

理由最好在开发现场留下，而非删除 Worktree 时追忆。值得长期保留的决策，用简短记录说明“遇到什么问题、有什么约束、比较了什么、为什么选它、付出什么代价、验证到哪里、何时重审”；条件改变再补后继记录。可从实际讨论提炼，无需用户另填整理提示词，也不要求每次机械操作写文档；现场没留下的动机，事后只能标未知并找当事人或原始讨论核对。

## 消化：形成能支持判断的知识

编纂者先建立资料清单，逐条识别可复用主张，再按主题综合。保留规则、理由、约束、反例和验证依据；压缩重复叙述。索引回答“哪个问题去哪里找”，主题回答“怎么理解和使用”，来源回答“凭什么这样说”。

同一知识集中表达，其他入口用链接；不能在核心表格、背景、概览、建议和变化中反复写相同事实。通用核对限制只声明一次，不给每条便签套满一套空字段。小批量短记录应形成紧凑文档，篇幅随有效知识量变化；评估检查实际重复和可用性，不能用固定字数取代内容判断。

每项重要主张分别表达三个维度，不能合成一个“可信度分数”：

| 维度 | 内容 |
| --- | --- |
| 适用条件 | 模块、业务场景、阶段、分支/版本、环境；未知就说明 |
| 证据性质 | 来源记录、本次代码静态核对、综合推断、建议；是否实际运行验证另记 |
| 适用状态 | 当前适用、历史有效、已替代、已证伪、待核实 |

“证据清楚”可能只证明某项历史决策确实存在，不证明当前适用；“已经替代”也不证明当时选错。当前代码、产品规则和历史决策分别支持不同种类的主张：代码能证明实现，不能单独证明业务应该如此或当时为什么如此。

按实际需求建立关联：业务规则约束模块，模块依赖影响变更，决策解释实现，问题经验提示验证。关联必须说明理由，不能为了构成知识图谱添加无依据的连线。

## 修改：先比较条件，再决定动作

新材料不是简单追加摘要，更不是以最新文件覆盖旧结论。

| 情况 | 修订动作 |
| --- | --- |
| 新问题或新事实 | 新增知识单元，附来源与边界 |
| 同一主张和条件重复出现 | 合并表述、保留来源；不因此提高真实性 |
| 同一主题适用于不同阶段、分支或环境 | 补充条件、并存表达；不误判为冲突 |
| 原结论表达过宽或不准确 | 纠错或收窄范围，说明依据 |
| 明确的新决策改变旧做法 | 记录替代链：旧做法→原理由→变化条件/证据→新做法 |
| 证据推翻原事实主张 | 标已证伪并说明证据，防止再次被引用为事实 |
| 证据冲突或不足 | 暂缓裁决，列双方来源、影响和需要补的证据 |

保留稳定主题 ID；改名/合并留旧入口。判断替代依靠明确的范围和决策/实现证据，不能凭文件顺序、采集时间、修改时间或多数意见。旧原文不在本轮输入时，保留历史入口并标待核实，先找回证据，不能用旧报告自证。

维护者的语义更正或新决策也应成为可追溯的新资料：注明原主题、改成什么、为什么、适用条件及依据；未记录的理由仍明确留缺口。只改生成稿，下一轮不能靠它自证。错别字和排版不需要制造决策记录。已批准的目标规则与当前实现分别说明，批准不等于实现完成；两者不一致时留下待实施或核对项。

例：开发阶段为赶试用采用串行任务，原因是外部配额且团队无值班能力；维护阶段配额放开并要求吞吐，于是换队列。知识要保留原约束、缓解效果和代价，说明替换条件；“队列通常更好”不能推翻当时选择。此例是设计示例，不是 AILoom 仓库事实。

## 评估：用原文和问题检验结果

生成者自检之后，应用另起独立上下文，使用所选本机 CLI 对同一批原始输入、来源背景、相关代码、旧稿及阶段处理记录复核；不承接生成者会话，也不要求使用另一家模型。AI 评估仍需要证据，不能当成人工批准。默认[整理提示词](../../src/knowledge/res/organize-wiki.md)负责编纂，[评估提示词](../../src/knowledge/res/review-wiki.md)负责审查，不能互相代替。

每批及最终来源页区分已读采用、合并/去重、沿用并核验、历史保留、已读未采用、尚未读取、读取失败及冲突待核实，并说明定位、理由、对应主题和代码核对范围。采集程序的读取记录不等于 AI 研读；未列状态视为未知。AI 评估检查错误跳过、关键遗漏及处理理由，不能只核对来源数量。当前研读深度仍由编纂者声明并由评估者核对，未提供逐次文件读取的自动审计证明。

评估返回通过、需修订或资料不足。格式有差异时兼容自然语言结论；结论不明确或相互矛盾则再次请评估者核对，而非直接报格式错误或猜测通过。需要修订时把具体缺陷、证据与完整候选稿交回工具，修订后重新独立评估，同时检查新增遗漏；资料不足或仍未确认则保留候选稿与评估，当前 Wiki 不替换。评估及修订共用本轮时间预算，到收尾边界保留进度继续，完整候选稿可直接续评，不先重新生成全稿。

通过后才原子保存页面、`wiki/review.md`（同名人工文件存在时使用独立评估文件）与 `.ailoom/review.json`。评估元数据绑定项目/知识集合 ID、候选稿摘要、原文及旧 Wiki 输入摘要、提示词摘要和最终发布文件摘要；发布前再次检查输入及人工改动。生成的主题标 `ai_reviewed`，只表示对应内容通过本轮 AI 评估；历史未评估稿不追认，后续未评估保存也不沿用旧评估。当前代码核对范围以评估记录为准，尚无全量代码内容冻结与后续自动失效机制。

评估输入还需明确候选稿位置与最终发布位置。候选稿可暂存在库外，正文相对链接按目标发布目录核对，不能因临时存放位置不同误判失效；原始目标文件是否真实存在仍须逐个核对。编纂传输稿的原文链接以虚拟 `docs/organized/` 为基准；应用保存时改写为实际 Wiki 页面路径。评估已保存页面时按各页面的真实位置核对，索引及跨页目标也须存在。

评估先从原文建立关键知识清单，再看整理稿，避免只检查它自己选择保留的内容。逐项核对会影响业务行为、设计取舍和后续行动的主张；核对所有来源是否读取/合理合并/明确无法读取，检查来源是否真的支持结论。不能仅以“每份文件有一行来源”证明知识覆盖。

必须退回的情况：编造理由或验证结果；把实验、建议或历史做法当现状；丢失关键业务例外、约束、代价或原决策理由；无证据裁决冲突；错误引用、自引或无出处的重要断言。一般排版问题与这些问题分开报告。资料本身未记录原因而稿件明确保留缺口，可以合格，不应逼模型补造。

至少用这些任务检查可用性：

- 为什么这里采用看似次优的方案？原因有记录吗？
- 当前主分支维护时应该怎么做，实验分支是否不同？
- 业务正常路径和关键异常如何处理，改动影响哪些模块？
- 哪项旧结论已被替代，为什么，是否意味着当时错误？
- 什么变化需要重新审查，哪个问题还没有答案？

每个回答应能定位主题与原始证据。评估输出通过、需修订或评估资料不足；每项缺陷给出主张、位置、证据、影响、修订要求。必须项失败就用同一批来源修订并再次核对，保留原评估问题，防止只改措辞；修复时同时检查有无引入新的业务遗漏或范围错误。不能用总分抵消关键错误。

## 使用与再次审查

AI 先按索引找到主题，再读取适用条件、证据、历史和问题，不直接把历史/未知/建议当指令。文档写着“当前”也需要结合这次任务的分支、版本和代码确认。

代码契约、产品规则、外部约束或来源资料改变时，受影响的知识应进入待复核；变化本身不等于知识错误。目标机制需绑定资料摘要、核对的代码版本/未提交状态、提示词版本和评估记录，避免对 A 输入通过后误用于 B 输入。仅按天数判过期或按改动行数自动重写都不足以证明质量。

## 当前实现与后续顺序

| 部分 | 当前情况 |
| --- | --- |
| 采集 | 开始整理时自动汇集可用工作目录及其子目录的候选文档，无需先扫描或勾选；不可变原文、来源背景和修订历史保留，来源删除后快照仍保留 |
| 编纂 | 内置默认提示词，无需用户填写；读取当前资料和旧报告，保存项目索引、独立模块/问题页及来源、建议、问题、变更页；传输稿仍为受约束 Markdown |
| 资料历史 | 当前候选与已登记历史出处分开按需读取；历史快照引用核对项目归属和内容摘要，不能自动提升为当前实现或恢复用户停用的资料 |
| 自检 | 编纂记录资料处理、代码核对、演变与自检；结构/引用检查不能替代内容评估，候选稿尚未保存为当前知识 |
| 独立评估 | 后台已串联独立上下文评估、按缺陷修订与重新评估；每轮候选稿、结论、证据和未完成正文留在任务记录 |
| 发布与检索 | 新整理通过 AI 评估后才替换当前 Wiki；未通过保留候选稿和旧 Wiki。历史 unreviewed 内容仍可能被检索，不追认为通过；尚无全库状态过滤或旧稿自动补评 |
| 变化检测 | 生成期间库内资料或旧报告变化会拒绝覆盖；代码变动、生成后的资料变化尚不会自动标过期或阻断检索 |

下一步按真实能力闭环实施，不能只给 UI 增加“可信”标签：

1. **先固定编纂标准并评估样例**：落实本文默认提示词，用[验收样例](../fixtures/knowledge/development-lifecycle/README.md)检查取舍、阶段、冲突、未知及旧稿纠错。本步不等于运行时门禁完成。
2. **继续完善评估版本与变化检测**：候选稿、原始输入、提示词与发布文件已绑定；还需补齐实际核对代码的精确版本/内容变化追踪、历史未评估稿处理与检索状态过滤。不能把“已有 AI 评估”描述为已经覆盖这些能力。
3. **补齐历史证据与按模块复核**：受控提供当前项目的历史快照及修订关系；代码/业务/约束改变触发受影响主题复核，并同步检索状态。保留原始出处、稳定入口及评估记录。

设计依据：[Karpathy LLM Wiki](../research/KARPATHY-LLM-WIKI.md) 的原始资料与综合知识分离、[Magpie](../research/MAGPIE-DEVELOPMENT-KNOWLEDGE.md) 的契约/理由/经验证据、[Cindy](../research/CINDY-DEVELOPMENT-KNOWLEDGE.md) 的业务规则/当前约定/历史决策区分。这里的生命周期和验收规则是 AILoom 自身设计，不能据此声称参考项目有相同自动化能力。
