## 背景

返工轮次复盘中确认的两个接入摩擦点：①"管理员"需要手写 `ailoom.toml`，无脚手架引导；
② 发布链路只有设计稿，无 CI 矩阵构建。本卡补齐两者的**本地准备**部分。

## 交付

1. `ailoom source` 脚手架命令：生成 `ailoom.toml` + `resources/` 九类目录骨架，
   可选示例资源（`--minimal` 关闭）、`--git` 初始化仓库、`--force` 合并生成
   （已存在文件跳过不覆盖）；生成后用真实清单加载器 + 资源枚举自校验。
2. `.github/workflows/release.yml`：三平台五三元组矩阵构建
   （darwin arm64/x64、linux x64/arm64、windows x64），产物命名与
   `packaging/npm/cli.js`、`scripts/install.sh` 对齐（`ailoom-<triple>` + `.sha256`）；
   手动触发默认只构建上传 artifacts；GitHub Release 仅在显式 `publish=true` 时创建。

## 验收标准

- [x] 脚手架产物能被 `ailoom init --local-path ../team-src` 直接绑定并 `sync` 成功，
      示例资源真实部署到宿主路径（tests/source_init.rs::scaffold_then_bind_and_sync_end_to_end）。
- [x] 已有清单目录默认拒绝覆盖；`--force` 合并；非法 team_id 拒绝
      （scaffold_rejects_overwrite_and_invalid_ids）。
- [x] `--minimal` 只生成骨架（scaffold_minimal_has_no_examples）。
- [x] release workflow 不含任何自动发布路径；Release 步骤需显式输入与维护者配置的
      RELEASE_TOKEN（缺失即失败=未授权），npm publish 仍为独立授权动作。
- [x] fmt / Clippy / 全量测试通过（见 evidence/logs）。

## 实施边界

- 不执行真实 npm publish / GitHub Release（独立授权动作，记录于 AIL-029 后置事项）。
- 不改动团队协作模型（AIL-030 等设计不变）。
